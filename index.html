01.3 Active experiment

Compiler tooling

RealLang

2025 — present

A working language and compiler-front-end experiment built around a practical question: can compiler errors be precise enough for both people and software to act on?

What I built

  • Lexer, recursive-descent parser, and typed syntax tree
  • Type checking across the compiler pipeline
  • Structured diagnostics designed for programmatic repair
  • A testable path from source text to checked program

Private research project · code walkthrough available on request

Compiler path / current
  1. 01Source
  2. 02Lexer
  3. 03Parser
  4. 04Type check
  5. 05Structured diagnostics

Diagnostics carry a location, cause, and repair-oriented structure—not only a line of prose.

Engineering notes +

Question

Traditional diagnostics explain a failure to a person. What changes when a tool also needs to apply the repair?

Decision

Represent diagnostics as structured records, then keep the front end explicit enough to recover and continue checking.

Current edge

The compiler works end to end through type checking; the experiment now lives in the quality of its error recovery and fixes.

How I got here.

I started in game development, where state, latency, and failure are immediately visible to the person on the other side of the screen. Since co-founding Imagicast in 2021, I’ve expanded from gameplay systems into infrastructure, languages, and developer tools.

I like understanding where state lives, what happens when a dependency disappears, how a change gets rolled back, and whether the next engineer can tell what the system is doing.

I’m looking for a Summer 2027 software engineering internship on a team that ships real systems and gives early-career engineers meaningful problems to own.
